# docs/evidence — スクリーンショットの置き場

**BACKLOG B24 / B33 の恒久策。** ここに置くスクショの作り方・追跡してよい条件・限界を書く。

## 何が問題だったか

一覧・詳細・統計・産地の画面には **(日付, 銘柄, 都道府県) が同じ行に写る**。これは B18 で
「コミットした2つの射影から復元できた」と問題にした**飲酒台帳の結合キーそのもの**。しかも
**PNG は画素なので `npm run ledger:check`(テキスト検査)は中身を1バイトも読めない** =
混入しても CI は緑になる(B24)。

結果、brain の品質バー「390px / 1280px のスクショを証拠にする」と「台帳を公開しない」が
正面衝突し、Phase 3〜6 の完了条件のスクショが**すべて未達のまま積んだ**(B33)。

## 決めたこと

**証拠の種類で分担する。**

| 何を | どうやって | どこに残す |
|------|-----------|-----------|
| **数値**(203本 / 年別 / 県別34区分 / 分母 185→190 / 横あふれ0) | **実データ**を実ブラウザに入れて **DOM を実測**する | `docs/phases/PHASE_*.md` の本文(コマンド出力・実測値) |
| **見た目**(レイアウト・折り返し・情報密度・下端の切れ) | **合成データ**を取り込んだ画面を撮る | `docs/evidence/demo-*.png`(追跡する) |

実データのスクショは**撮ってもよいが追跡しない**(`.gitignore` の既定が「追跡しない」)。

### 合成データで**出ない**もの(限界。埋めない)

- 203行の一覧をスクロールしたときの体裁(合成データは 27件)
- 34区分198本の県別一覧の高さ / 47県の一覧の折り返し(合成データは 23区分25本)
- 延べ314本のスタイル分布で棒が潰れる・軸ラベルが重なる現象
- 実 iPhone の写真(EXIF 回転)・実 HEIC(→ B34。実機でしか回収できない)

**これらは合成データの件数では再現しない。**「スクショがあるから見た目は確認済み」と読まない。
実データでの体裁は DOM 実測(高さ・`scrollWidth - clientWidth`・件数)で見ること。

## 追跡してよいスクショの条件

1. **記録0件の空状態**、または
2. **`docs/evidence/demo-backup.json`(合成データ)だけを取り込んだ画面**

`.gitignore` は `docs/evidence/*.png` を既定で無視し、上の条件を満たす**個別のファイル名だけ**を
`!` で戻す。この `!` の列挙が allowlist の**単一の出所**で、`scripts/check-ledger-leak.mjs` が
「index に載っている `docs/evidence/` の画像がこの列挙と一致するか」を検査する。

**新しいスクショを追跡するときの手順(飛ばさない)**

1. 撮る(下の「撮り方」)
2. **1枚ずつ画像を開いて目で見る。** 台帳の日付・銘柄・店名が写っていないことを確認する
   (画素は grep できない。**この目視が唯一の検査**)
3. `.gitignore` に `!docs/evidence/<名前>.png` を足す
4. `npm run ledger:check` が緑になることを確認する

### この仕組みで防げないこと

- **許可済みの名前のまま中身を実データのスクショに差し替える**こと。画素は読めないので
  検出できない(ファイル単位の名前 allowlist の原理的な限界)。撮り直したら 2 をやり直す。
- 目視の見落とし。合成データ以外を1枚でも混ぜないことが前提。

## 撮り方(再現手順)

```bash
npm run demo:data                         # docs/evidence/demo-backup.json を作る(決定的)
node scripts/make-demo-backup.mjs --check # 既存ファイルが生成結果と一致するか見る
npm run dev -- --port 5178 --strictPort
```

ブラウザで `http://localhost:5178/` を開き、

1. 「取り込み / 書き出し」→「取り込む JSON ファイル」で `docs/evidence/demo-backup.json` を選ぶ
2. 読んだ内容(記録 27件 / エイリアス 2件)を確認して「取り込む」
   — **デモ投入専用の裏口は作っていない**。本番と同じ2段の取り込みを通す
3. 幅 390px と 1280px で、4タブ(記録 / 統計 / 味 / 産地)をビューポート撮影する

撮影は**ビューポート**(全ページではない)。下端のタブバーが切れていないこと・
折り返しが破綻していないことを、実機で見るのと同じ切り取りで見るため。

### 合成データの中身と、それが満たす不変条件

`scripts/make-demo-backup.mjs` が生成する 27件。生成時と `ledger:check` の**両方**が検査する:

1. `drankOn` が**台帳の日付集合と交わらない**(台帳は 2020..2026 / 合成は 2017..2019)
2. 銘柄表記・銘柄名が**台帳の銘柄集合(94種)と1つも一致しない**

都道府県だけは実在の県名を使う(産地の塗り分けの証拠に要る)。県名は
`linkBrand.cases.json` で公開済みの列で、**日付と同居しなければ結合キーにならない** —
1 によって同居し得ない。`place` は全行に「デモ」を含めてあるので、
**スクショ1枚だけを見ても合成データだと分かる**。

銘柄はさけのわの公開マスタから採った実在の銘柄(架空名だと `sakenowaBrandId` が引けず、
味タブのレーダー・散布図が空になって証拠にならない)。**実在するが本人が飲んでいない銘柄 ×
架空の日付・場所・備考**という組み合わせ。

`--check` を `npm run invariants` に入れていないのは、生成物が上流(さけのわ)の銘柄IDに
依存するため。上流が銘柄を消した日に**月次更新ジョブがデモ用 fixture のせいで赤になる**のは
割に合わない。CI が守るのは**生成の由来ではなく中身**(上の不変条件2つ)。
