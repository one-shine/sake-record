実装計画。`docs/SPEC.md`（受け入れ基準17項目 / e2e手順15ステップ）を入力に作った。**大規模のため7フェーズに分割**し、詳細は `docs/phases/PHASE_n.md` に切り出す。ここはフェーズ index。

### さけのわ API（実取得して確認）

`Access-Control-Allow-Origin` ヘッダが無いことを確認した。ビルド時取得＋コミットは回避不能な決定。

| endpoint | 件数 | 生サイズ |
|---|--:|--:|
| brands | 3264 | 156KB |
| flavorCharts | 1344 | 218KB |
| breweries | 1749 | 81KB |
| areas | 48（JIS県コード1〜47 + id 0「その他」）| 1.4KB |
| flavorTags | 141 | 4KB |
| brandFlavorTags | 2970 | 147KB |

各レスポンスに `copyright: "Sakenowa"` と `etag` / `last-modified` がある（月次更新の差分判定に使える）。

**サイズ**: 素のスリム化では gzip 170KB で受け入れ基準（≤200KB）に張り付く。**タプル化 + フレーバー値を0〜100の整数に丸める**と **gzip 約92KB / raw 232KB** に落ちる（areas 0.4 / breweries 15.9 / brands 35.7 / flavorTags 1.3 / brandFlavorTags 26.8 / flavorCharts 11.7 KB）。タプル化を採る。

**銘柄名は一意でない**: 3264件に対し異なる名前は3196件。54個の名前が複数銘柄を持ち、**都道府県で絞っても25グループが曖昧なまま残る**（`高砂` は静岡/三重/佐賀/島根の4件）。`linkBrand` の `candidates[]` 返却は飾りではなく必須経路。

### 紐付け（プロトタイプを実装して全203本で実測）

`normalize`（NFKC → 括弧内除去 → 空白除去 → 異体字マップ → lowercase）+ エイリアス8件 + 都道府県絞り込み:

```
auto 173 + alias 13 = 186本紐付け / unlinked 12 / unknown 5(不明)
```

正規化は安全: 銘柄マスタ側で新たに生じる衝突は12〜14件だけで、ほぼ全てが同一県内の表記ゆれ（`丹沢山`/`丹澤山` 神奈川、`寿`/`壽` 山形など）。県を跨ぐのは `磐城壽`(福島) vs `磐城寿`(山形) の1件のみで、これは都道府県で解決できる。

**決定的な設計判断**: 「記録に都道府県があるなら、県が一致する候補だけを採用する。**0件になっても全件にフォールバックしない**」。brain `coding-conventions.md`「キーが定義域外のときルックアップが全件にフォールバックしてはならない」の直接適用。守らないと `Beau Michelle`（ログ:神奈川/川西屋酒造）が別物の `Beau Michelle`(3141, 長野/伴野酒造) に**誤って自動紐付けされる**。厳格化すると 3141 を候補提示したまま `unlinked` に留まり、SPEC の意図どおりになる。

**変異テストの結果 — エイリアス8件のうち2件は既に冗長だった**（1件ずつ抜いて再測）:

| エントリ | 抜くと | 判定 |
|---|--:|---|
| 赤武 | −4本 | 必須 |
| 寒菊 | −2本 | 必須 |
| ZEBRA / MAGMA / 荷札酒 / 会津宮泉 | 各 −1本 | 必須 |
| **髙砂/三重県** | 186 → 186 | **冗長**（異体字 `髙→高` + 三重県で4候補から一意に絞れる） |
| **ゆきのまゆ** | 186 → 186 | **冗長**（さけのわ名 `ゆきのまゆ（醸す森）` が括弧除去で一致する） |
| 表を空に | 186 → **176** | |

8件は安全網として保持する。ただしテストは「8件すべてが紐付け数を増やす」と書くと**落ちる**。「表を空にすると 186→176」+「必須6件は各々減る」+「冗長2件は現状冗長であることを固定」と書く。冗長側が将来変化したらテストが教えてくれる。

### ログ側の統計（`sake-log.md` のサマリを再計算して全一致を確認）

年別 2020:1 / 2021:12 / 2022:65 / 2023:33 / 2024:31 / 2025:33 / 2026:28（計203）。福島県22 / 和歌山県20 / 山形県17。スペック出現数も一致。**実装が再現すべき癖**:

- **スタイル集計は排他バケツではなく重複する部分文字列カウント**（`大吟醸45` は `純米大吟醸43` を含み、`原酒16` は `生原酒15` を含む）。合計が203を超えるのが正しい → UI に「重複計上」と明記する
- **スペック列のみが対象**。備考を含めると `にごり` が 4→5 にずれる
- 都道府県別サマリは**34バケツ・合計198**（空欄5本を除外し `静岡県または京都府` は独立バケツ）

ログの都道府県値35種のうち、空欄5本と `静岡県または京都府` 1本以外は**全て さけのわ areas 名と完全一致**した。`@svg-maps/japan` の47 romaji id（`aichi` `akita` …）と JIS コード1〜47 の**全単射マップを構築して漏れ0を確認済み**。日本語県名は さけのわ areas を単一の出所にする。

### ログのパース時に効く不規則性

`## 全記録` 見出しを起点に `^\| \d+ \|` の行だけ拾う（ファイルには他に2つ表があり「最初の表」を取ると壊れる）。全203行がちょうど6セル、`|` を含むセルは無く、空セルは半角スペース2つ（全セル trim 必須）。日付は全て `YYYY-MM-DD` で単調非減少。

- `不明` 5本 = センチネル → `unknown`
- `英君 または 英勲` / `静岡県または京都府`（1本）→ 手動紐付け対象
- NFKC が畳まない異体字 `髙` `寫` `冨`
- **重複に見えて重複でない2組**（同日・同銘柄で内容も同じ2件が2組 = 同一ボトルの表/裏ラベル写真。**どの日付・銘柄かは書かない** — `(日付, 銘柄)` の対は台帳の復元キーなので docs に置かない）。`(日付, 銘柄)` で dedupe すると203が崩れる
- 同日に最大6〜7本 → `drankOn` は一意でない
- **写真は1枚も無い**（画像ファイル・パスとも存在せず、元 xlsx もリポジトリ外）→ 203本は `thumbnail: null` で取り込む

**既に踏まれている罠（コピーせず、修正を写す）**

- `npm run check` はどのプロジェクトにも存在しない → `tsc -b && eslint .` を新規に作る
- prettier は入れない（poker-gto に無く、途中導入は差分を荒らす）。整形は eslint に任せる

## 設計方針

### 依存方向

`src/domain/`（React 非依存の純TS）← `src/store/` ← `src/ui/`。ドメイン層は外部依存ゼロで単体テストする。brain `architecture-decisions.md` の絶対ルール。

### `base` とルーティング: `base: './'` + URL ルーティングなし

- `'./'` は**ブランド名もリポジトリ名もビルド設定から消す**（受け入れ基準「ブランド名が base と表示文字列以外に出現しない」を SPEC の要求より厳しく満たす）。副産物として **Phase 1 の実装がリポジトリ名の決定を待たない**
- dev もルート配信になり、poker-gto の「dev がサブパス配信で素の `/` が404」という日常の摩擦が消える
- **相対 base と history ルーティングは併用禁止**: 文書 URL が `/repo/foo/bar` になると `./sw.js` が `/repo/foo/sw.js` に解決されて壊れる。ネストしたパスを作らない構成とだけ両立する
- ハッシュルーティングも相対 base と安全に共存するが**買うものが無い** — SPEC は共有機能を恒久スコープ外と宣言しており、共有する URL が存在しない。`404.html` の裏技も不要になる
- **ルーティングなしの唯一の実損は戻るボタン**（Android/PWA で戻るとモーダルが閉じずアプリが終わる）→ オーバーレイを開くときだけ `history.pushState(null,'',location.href)` し `popstate` で閉じる。URL は変わらないので相対 base は無傷
- 4タブなら状態管理ライブラリは不要（`useState` + Context。依存を増やさない SPEC 方針に沿う）

### `linkBrand` を二重実装しない

brain「依存の都合で再実装するなら等価テストを書く。暗黙の再実装は必ずドリフトする」への対処 — **そもそも紐付けをスクリプト側に置かない**。

- `scripts/import-sake-log.mjs` … **markdown → 行JSON の射影のみ**。紐付け0・集計0。検証は*パース*不変条件だけ（203件 / 6セル / `No.` 1..203連番 / 日付形式 / 単調非減少）
- `src/domain/linkBrand.ts` … 紐付けの**唯一の実装**。取り込み時にブラウザ側で走るので、ユーザーが画面で見る数字を出すコードがそのままテスト対象になる
- 集計も同じ規律で `src/domain/stats.ts` のみ。スクリプトに年別ヒストグラム検証を入れたくなるが**入れない**（二重実装の入口）
- `tsx` は入れない（この分割なら `.mjs` から `.ts` を import する必要がない）

**SPEC のシグネチャ `linkBrand(label, prefecture)` はそのままでは実装できない**（銘柄マスタとランタイムエイリアスを注入できず純関数にならない）→ `createLinker({brands, breweries, areas, aliases}) => (label, prefecture) => Result`。呼び出し側の形は SPEC 通りに保たれる。

### 生成データの置き場所: `src/data/` → **`public/data/`**（SPEC からの逸脱）

1. **オフライン保証が確実になる。** SW の原子的 SHELL に `./data/sakenowa/*.json` という**安定した既知パス6本**を書ける。`src/` に置くとハッシュ付き JS チャンクになり、`inject-sw-precache.mjs` が vite manifest を解析して正しいチャンクを特定しないとオフライン新規作成が壊れる。best-effort 層に落ちると「起動は成功するがサジェストが空」という最悪の半端な状態になる
2. 月次データ更新が **JS バンドルのハッシュを変えない** → 差分が data だけになる
3. 232KB の JSON を tsc の入力から外せる / エントリ JS が小さく保たれる

代償は起動時の非同期ロード1回だけ。記録に `brandName` を非正規化保存するので Timeline はテーブル未着でも描ける。**SPEC 本文の追随は BACKLOG B2。**

### 不確実性の表示

`linkStatus` のバッジ対応表を**1箇所に集約**し、迷ったら格下げする（brain）。**`unlinked`/`unknown` にフレーバー値を推定で埋めない。** **紐付け済み(186) ≠ フレーバー取得済み(185)** なので、6軸集計の分母は「フレーバー取得済み件数」を出す。

### クレジットは2件になる

1. **さけのわデータ** — クレジット + `https://sakenowa.com` へのリンク（省略は禁止事項）
2. **`@svg-maps/japan`** — CC-BY-4.0。作者 Victor Cazanave / タイトル / ライセンスリンク / 改変の明示

`scripts/check-attribution.mjs` は**両方 + `noindex`** を成果物で検証する。クレジットは React が実行時に描くので **`dist/assets/*.js` を見る**（`dist/index.html` には入っていない）。実形状マップを選んだ副作用の緩和として、産地マップには**都道府県の一覧表を併置**する（香川・大阪のような小県のタップ標的が数pxしかないため）。

### 順序の根拠

- **Phase 1 に公開経路と PWA を入れる。** 紐付け・サイズ・パースは計画時の実測で**既にリスクが退治済み**であり、Phase 2-3 はそれを転写するだけ。未検証の実リスクは (a) リサイズ/HEIC/EXIF、(b) Blob の JSON 往復、(c) エイリアス合成、(d) 実機オフライン、そして (e) **Pages/リポジトリ設定という外部システム**。Pages が private で 422 になることを最終フェーズで知るのが最悪なので最初に通す。SW は動いている実装のコピーなので安い
- **初めて画面が出るのを Phase 3 に。** 無画面のフェーズが続くと brain `development-workflow.md` が要求するスクショ証拠なしにレビューが回り、203本が*どう見えるか*を永続化層が固まった後に知ることになる。IndexedDB は203本を見る前提条件ではない（パーサと `linkBrand` が前提条件）
- **手動紐付け(5)を集計画面(6)より前に。** SPEC は e2e手順10と12を中核と宣言している。手順12（寫楽を紐付け→分母 185→190）は、FlavorMap を作る時点で手動紐付けが既にあって初めて**一続きの観測**になる
- **写真リサイズをフォームと同じフェーズに。** 永続化層と一緒にすると、置き場のない状態でサムネイル配線を作って後で繋ぎ直すことになる
