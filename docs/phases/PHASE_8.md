# PHASE 8 — 端末間で記録を同期する（サーバを立てる）

## なぜこのフェーズが要るのか（前提の変更）

利用者の報告: 「登録データが永続するようにしたい。スマホで見ると登録されていない」。切り分けた結果は
**「別の端末で登録したものがスマホで見えない」** で、これは不具合ではなく**設計どおり**だった。

- 記録は**その端末の IndexedDB だけ**に入る。サーバは無い。
- 端末間の移動は JSON の書き出し / 取り込み（手動）。

利用者は**自動で同期したい**と決めた。これは `docs/SPEC.md` と `CLAUDE.md` に書いてある
**「認証・クラウド同期・SNS共有は恒久的にスコープ外」という設計判断の変更**であり、
このフェーズはその変更を前提に立てる。

> **着手前に必ず: `docs/SPEC.md` と `CLAUDE.md` の「恒久的にスコープ外」の記述を改訂する。**
> 実装だけ入れて文書が古いまま残ると、次に読む人（と将来の自分）が矛盾した2つの規範を持つことになる。
> **「個人の飲酒記録を端末内に閉じる」をやめる**という判断を、理由つきで文書に残すこと。

## 目的 / 完了条件

**スマホと PC で同じ一覧が見える。片方で足した記録がもう片方に出て、片方で消した記録が復活しない。**

完了条件（受け入れ基準の追加案。SPEC 改訂時に採番する）:

| #   | 条件                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------ |
| S1  | 端末Aで作った記録が、端末Bで同期後に出る（写真つきで）                                                       |
| S2  | 端末Aで消した記録が、端末Bで同期後に消える。**次の同期で復活しない**                                         |
| S3  | 同じ記録を両端末で編集したら、**`updatedAt` が新しいほうが残る**。負けた側は黙って消さず、理由を出す         |
| S4  | オフラインでも記録は作れて、オンラインに戻ったときに送られる                                                 |
| S5  | **同期を設定していなくても、これまでどおり端末内だけで全機能が動く**（同期は足すものであって、前提にしない） |
| S6  | トークン無し / 誤ったトークンでは 401。記録は1文字も返らない                                                 |
| S7  | 写真が往復で失われない（A11 と同じ規律。Blob → 転送 → Blob）                                                 |

## 設計方針

### 1. 何を採るか — Cloudflare Workers + D1（推奨）

| 案                                                   | 中身                                                        | 採否                                                                              |
| ---------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **A. Cloudflare Workers + D1**                       | Worker が API、D1（SQLite）が記録と写真。認証は単一トークン | **推奨**                                                                          |
| B. Supabase                                          | Postgres + Storage + Auth（マジックリンク）。RLS で守る     | 過剰。利用者1人に対してアカウント・RLS・匿名キーの設計が要る                      |
| C. 全文書を1ファイルで置くだけ                       | 既存の export JSON をそのまま置いて上書き                   | **不可**。両端末が編集すると**片方の追加が丸ごと消える**（後述）                  |
| D. GitHub のプライベートリポジトリに JSON をコミット | サーバ不要                                                  | **不可**。書き込みトークンをクライアントに置くことになる。このリポジトリは public |

**A を推す理由**: 利用者は1人、記録は数百件、写真は1枚50KB以下。無料枠に収まり、**運用が要らない**
（静的サイトと同じく「置くだけ」）。D1 は SQLite なので、数百行のテキストと数MBの BLOB には十分で、
**最初は写真も D1 に BLOB で入れる**（R2 を足すと配線が増えるだけで、この規模では利点が無い）。

### 2. 同期の単位は「記録1件」。全文書の置き換えにしない

既存の export/import は**全文書の置き換え**で、これはバックアップとしては正しいが**同期には使えない**:
端末Aが5件、端末Bが3件持っている状態でBが書き戻すと、**Aの5件が消える**。

→ **記録ごとに `updatedAt` で新しいほうを採る（last-writer-wins）。**
`SakeRecord` は既に `updatedAt`（ISO8601）を持っているので、新しい概念を足さずに済む。

### 3. 削除にはトゥームストーンが要る

いまの削除は**ハード削除**で、消した事実がどこにも残らない。同期を足すと
**「Aで消す → Bと同期 → Bにはまだ在る → Aに復活する」**が必ず起きる。

→ サーバに `deleted_at` を持ち、**削除も1つの変更として送る**。
→ **クライアント側にも削除ログが要る**。オフラインで消した分は、次の push まで「消したこと」を
覚えておかないと送れない（覚えていないと次の pull で復活する）。

### 4. 突き合わせは純関数で domain に置く

`src/domain/syncMerge.ts` に「ローカルの一覧 + サーバの変更分 → 適用すべき操作」を**純関数**で書く。
サーバも fetch も要らない形にすれば、**2端末を用意しなくても分岐を全部テストできる**
（`createLinker` / `createReadingIndex` と同じ注入形の規律）。

`src/store/sync.ts` は「fetch する / IndexedDB に書く」だけを持ち、判断を持たない。

### 5. 認証は単一トークン

利用者は1人なので、アカウントも招待も要らない。

- サーバ: `env.SYNC_TOKEN`（Worker の secret）と**定数時間で比較**する。
- クライアント: 端末ごとに1回だけ貼り付け、IndexedDB の `meta` に持つ。
- **URL は秘密にしない**（`src/config/app.ts` の定数でよい）。秘密はトークンだけ。
  これで **`.env` を使わない方針を維持できる**（`CLAUDE.md` の「環境変数を必要としない」は保てる）。

**限界を明示すること**: 端末を盗られたらトークンごと読まれる。ただし端末の IndexedDB には
記録そのものが既に入っているので、**追加のリスクは実質増えない**。この判断を SPEC に書く。

### 6. 写真は本体と分けて運ぶ

203件の export JSON は**写真を data URL で含むと約13MB**になる。同期のたびに往復させる大きさではない。

- 記録の本体（テキスト）… 数百件で数十KB。毎回まとめて往復してよい。
- サムネイル … 別のエンドポイントで**必要な分だけ**取る（`thumbnailUpdatedAt` を見て差分だけ）。

## サーバ API（案）

認証はすべて `Authorization: Bearer <token>`。

| メソッド | パス                       | 用途                                                              |
| -------- | -------------------------- | ----------------------------------------------------------------- |
| `GET`    | `/changes?since=<ISO8601>` | `since` 以降に変わった記録とエイリアス（**削除を含む**）を返す    |
| `POST`   | `/changes`                 | ローカルの変更分を送る。サーバは `updatedAt` が新しいときだけ採る |
| `GET`    | `/thumb/{id}`              | サムネイル1件（`image/jpeg`）                                     |
| `PUT`    | `/thumb/{id}`              | サムネイル1件                                                     |

D1 のスキーマ（案）:

```sql
CREATE TABLE records (
  id TEXT PRIMARY KEY,
  updated_at TEXT NOT NULL,      -- 突き合わせの鍵
  deleted_at TEXT,               -- トゥームストーン。NULL でなければ削除済み
  body TEXT NOT NULL,            -- SakeRecord から thumbnail を除いた JSON
  thumb BLOB,                    -- 長辺400px / 50KB以下
  thumb_updated_at TEXT
);
CREATE INDEX records_updated_at ON records (updated_at);

CREATE TABLE aliases (           -- 手動紐付けも同期する(A6 が端末間で失われないように)
  key TEXT PRIMARY KEY,
  updated_at TEXT NOT NULL,
  deleted_at TEXT,
  body TEXT NOT NULL
);
```

**`aliases` を落とさない**: 手動紐付けは「銘柄表記 → brandId」の判断で、記録1件に閉じない。
records だけ同期すると、片方の端末でだけ `寫楽` が `unlinked` に戻る（既存の export が
aliases を含めているのと同じ理由）。

## クライアントの変更

| ファイル                  | 変更                                                                                            |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `src/domain/syncMerge.ts` | **新規**。純関数の突き合わせ。ここが唯一の判断の置き場                                          |
| `src/store/db.ts`         | `DB_VERSION` 2 へ。`deletions` ストアを足す（削除ログ）。`meta` に `syncToken` / `lastSyncedAt` |
| `src/store/records.ts`    | `deleteRecord` が削除ログを残す                                                                 |
| `src/store/sync.ts`       | **新規**。pull / push / 写真の差分。判断は持たない                                              |
| `src/config/app.ts`       | 同期先の URL（秘密ではない）                                                                    |
| `src/ui/Sync/`            | **新規**。トークンの入力、最後に同期した時刻、手動同期、失敗の理由                              |
| `src/App.tsx`             | 起動時と保存後に同期を試す。**失敗しても記録は作れる**（S5）                                    |

**既存の規律を崩さない点**:

- 同期の失敗で**記録が作れなくなってはいけない**（`loadTables` が読み表の失敗だけ飲み込むのと同じ）。
- 同期していない端末では、いまとまったく同じ挙動になること（S5）。
- 競合で負けた側を**黙って消さない**（S3）。`unlinked` に推定値を埋めないのと同じ規律。

## 配備

**この環境から Cloudflare / Supabase の API に到達できない**（実測: `api.cloudflare.com` と
`api.supabase.com` は接続不能、`registry.npmjs.org` と `api.github.com` は 200）。

→ **デプロイは GitHub Actions から行う**（GitHub は到達可能）。`CLOUDFLARE_API_TOKEN` を
リポジトリの Actions secret に置く。**リポジトリには秘密を1文字も置かない**ので `.env` 禁止は維持できる。

→ **アカウントの用意・D1 の作成・トークンの発行は利用者本人の作業**になる（この環境からはできない）。
着手時に必要なものを列挙して渡すこと。

## 測ること / リスク

- **記録が端末外に出る。** これがこのフェーズの本質的な代償で、実装の巧拙では消えない。
  サーバの運用者は本人だが、「端末内に閉じる」という当初の約束はここで無くなる。
- **トークン1本の強度に全部が乗る。** 漏れたら記録が読まれる。長いランダム値にし、
  貼り付け以外の入力経路を作らないこと。
- **削除の復活は必ず一度は踏む。** ステップ3のテストを、実装より先に赤で見ること。
- 無料枠（D1 の行数・容量、Workers のリクエスト数）は個人利用なら十分だが、**着手時に実測して記録する**。
- 写真を D1 の BLOB に入れる判断は、**同梱データと同じく数字で見直す**（合計サイズが数百MBに
  向かうようなら R2 に移す）。
