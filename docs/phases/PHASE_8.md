## なぜこのフェーズが要るのか（前提の変更）

利用者の報告: 「登録データが永続するようにしたい。スマホで見ると登録されていない」。切り分けた結果は
**「別の端末で登録したものがスマホで見えない」** で、これは不具合ではなく**設計どおり**だった。

- 記録は**その端末の IndexedDB だけ**に入る。サーバは無い。
- 端末間の移動は JSON の書き出し / 取り込み（手動）。

利用者は 2026-08-01 に**自動で同期したい**と決めた。これは当初「恒久的にスコープ外」としていた判断の
変更で、**`docs/SPEC.md` と `CLAUDE.md` は改訂済み**（step 1 で実施）。線引きは1つずらしてある:

> **恒久的に残るのは「第三者のサービスに預けない」**のほうで、「端末から出さない」ではない。
> 記録は**本人が用意した同期先**にだけ出る。**この区別が崩れるとスコープ9（端末内 OCR）の根拠も
> 一緒に崩れる**ので、同期先は本人のものに限ることを条件として書いてある。
> 他人との共有・複数利用者は**恒久的にスコープ外のまま**。

### step 2 で作ったもの — `src/domain/syncMerge.ts`

**同期の判断はここ1箇所だけが持つ。** `fetch` も IndexedDB も持たないので、2端末を用意せずに
分岐を全部テストできる（これがこの設計の狙い。`createLinker` / `createReadingIndex` と同じ注入形）。

```ts
planSync({ local, localDeletions, remote, lastSyncedAt }): {
  applyLocal: string[]      // サーバの値でローカルを上書きする ID
  removeLocal: string[]     // ローカルから消す ID
  push: string[]            // サーバへ送る ID
  pushDeletions: string[]   // サーバへ削除として送る ID
  conflicts: { id, winner: 'local'|'remote', winnerDeleted: boolean }[]
}
```

**返すのは ID だけ。** 本体（JSON の組み立て・Blob の往復）は store 層の仕事で、ここに持ち込むと
テストがブラウザ API を要求し始める。

決めごと（コメントにも書いてある）:

1. **同期の単位は記録1件。** 全文書の置き換えにしない — 端末Aが5件・Bが3件のとき、Bが全文書を
   書き戻すと**Aの5件が消える**。既存の export/import はバックアップの形式であって同期には使えない
2. **`updatedAt` が新しいほうを採る**（last-writer-wins）。新しい概念を足さない
3. **削除も1つの変更。** サーバの `deletedAt` と**ローカルの削除ログ**の両方が要る
4. **同点は remote を採る。** 全端末が同じ値に収束するよう向きを1つに固定する。ローカルが負けたときは
   **黙って捨てず** `conflicts` で返す
5. **読めない時刻は最古として扱う。** 壊れた `updatedAt` が勝つと正しい記録が消える

### step 3 で作ったもの — 削除の記録

- `db.ts`: `DB_VERSION` 1 → **2**。`deletions` ストア（`{ id, deletedAt }` / keyPath `id`）を追加
- `records.ts`: `deleteRecord(id, deletedAt?)` が**同じトランザクションで**削除の記録を書く。
  別々のトランザクションに割ると「records からは消えたが削除の記録が残らない」状態が作れてしまい、
  その記録は**次の同期でサーバから復活する**（しかも画面上は正常に見える）
- `records.ts`: `listDeletions()` / `clearDeletions(ids)`。**送信が成功した id だけ**捨てる
  （まとめて全消しすると未送信の削除が黙って失われる）
- **版上げのテストがある**（`db.test.ts`）: version 1 の DB を手で作ってから開き直し、記録を1件も
  失わずに `deletions` だけが足されることを固定した。**既存の利用者が必ず通る道**なのでここは外さない

### 変異検証の記録（8件。**再実装するときは同じものを潰せること**）

削除ログを見ない / 同点をローカルの勝ちにする / 削除の時刻を見ず `updatedAt` だけで比べる /
前回の同期より古いものも送る / `NaN` の番人を外す / 削除の記録を書かない / `clearDeletions` が全消しする /
版上げで `upgrade` を飛ばす — の8つを入れると、それぞれ対応するテストが赤くなることを確認済み。

## 残りの段取り（step 4〜7）

### step 4 — Worker + D1（サーバ）

`server/` を新設する（アプリのビルドには含めない。`tsconfig` / `eslint` / `vite` の対象外に置くこと）。

**D1 のスキーマ**（`server/schema.sql`）:

```sql
CREATE TABLE records (
  id TEXT PRIMARY KEY,
  updated_at TEXT NOT NULL,      -- 突き合わせの鍵
  deleted_at TEXT,               -- 削除の記録。NULL でなければ削除済み
  body TEXT NOT NULL,            -- SakeRecord から thumbnail を除いた JSON
  thumb BLOB,                    -- 長辺400px / 50KB以下
  thumb_updated_at TEXT
);
CREATE INDEX records_updated_at ON records (updated_at);

CREATE TABLE aliases (           -- 手動紐付けも同期する
  key TEXT PRIMARY KEY,          -- aliasKey(label, prefecture)
  updated_at TEXT NOT NULL,
  deleted_at TEXT,
  body TEXT NOT NULL
);
```

**`aliases` を落とさないこと。** 手動紐付けは「銘柄表記 → brandId」の判断で記録1件に閉じない。
records だけ同期すると、片方の端末でだけ `寫楽` 5本が `unlinked` に戻る（既存の export が
aliases を含めているのと同じ理由）。

**API**（すべて `Authorization: Bearer <token>`）:

| メソッド | パス                       | 用途                                                                                                                              |
| -------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `GET`    | `/changes?since=<整数>`    | `since` より後に変わった records と aliases（**削除を含む**）。`hasMore` で続きを辿る                                             |
| `POST`   | `/changes`                 | 変更分を送る。**`updated_at` が新しいときだけ採る**（`ON CONFLICT DO UPDATE ... WHERE excluded.updated_at > records.updated_at`） |
| `GET`    | `/thumb/{id}`              | サムネイル1件（`image/jpeg`）                                                                                                     |
| `PUT`    | `/thumb/{id}`              | サムネイル1件                                                                                                                     |

**認証**: `env.SYNC_TOKEN`（Worker の secret）と**定数時間で比較**する。
`a === b` で書くと文字列比較が早期 return するのでタイミングが漏れる。長さを揃えてから XOR で畳むこと。

**【step 4 で変えた】位置は ISO8601 ではなく整数のカーソルにした。**
`updated_at` は端末が書いた値なので、時計がずれた端末が過去の時刻で書き込むと、そこを通り過ぎた
端末はその行を**二度と受け取らない**。サーバ側で単調増加させる整数（`cursor` 表 + 行ごとの `seq`）に
すれば端末の時計に依存しない。`GET /changes` は `cursor` を返し、クライアントは**push が成功してから**
それを保存する。`planSync` に渡す `lastSyncedAt`（端末の時計）とは**別の値**で、取り違えると
`Date.parse(42)` が2042年として通り、push が例外も無く空になる（実測）。

検証（`wrangler dev` + `curl` で足りる）:

- トークン無し / 誤りで **401**、本文が空
- 変更分の往復（`POST` → `GET ?since=` で戻る）
- 古い `updated_at` を送っても**上書きされない**
- サムネイルの往復（バイト列が一致する）

### step 5 — クライアントの同期層と UI

| ファイル            | 役割                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------- |
| `src/config/app.ts` | 同期先の URL 定数（**秘密ではない**。これで `.env` を使わない方針を保てる）                    |
| `src/store/sync.ts` | **新規**。pull / push / サムネイルの差分。**判断は持たない**（`planSync` に聞く）              |
| `src/ui/Sync/`      | **新規**。トークンの入力（貼り付けのみ）、最後に同期した時刻、手動同期、失敗の理由、競合の報告 |
| `src/App.tsx`       | 起動時と保存後に同期を試す                                                                     |

**崩してはいけない点**:

- **同期の失敗で記録が作れなくなってはいけない**（A28）。`loadTables` が読み表の失敗だけ飲み込むのと同じ
- **同期を設定していない端末は、いまとまったく同じ挙動**になること
- **競合で負けた側を黙って消さない**（A26）。`conflicts` を画面に出す
- トークンは `meta` ストアに置く。**貼り付け以外の入力経路を作らない**
- `lastSyncedAt` を進めるのは **push が成功した後だけ**。先に進めると未送信の変更が二度と送られない
- 送信に成功した削除だけ `clearDeletions` する

**取り込み（import）は削除の記録を作らない。** 全置換はバックアップの復元であって、同期先に対する
削除の意思表示ではない。取り込み後は次の同期でサーバ側と突き合わせて解決する（この判断を
`backup.ts` のコメントに残すこと）。

### step 6 — GitHub Actions からデプロイ

**この環境（Claude Code on the web）から Cloudflare / Supabase の API に到達できない**
（実測: `api.cloudflare.com` `api.supabase.com` は接続不能、`registry.npmjs.org` `api.github.com` は 200）。
**ローカルで作業するなら直接 `wrangler deploy` でよい。** Actions 経由は「この環境からも触れるようにする」
ための道で、必須ではない。

Actions にする場合: `CLOUDFLARE_API_TOKEN` を**リポジトリの Actions secret** に置く。
リポジトリには秘密を1文字も置かないので `.env` 禁止は維持できる。

## 測ること / リスク

- **記録が端末外に出る。** これがこのフェーズの本質的な代償で、実装の巧拙では消えない。
  サーバの運用者は本人だが、「端末内に閉じる」という当初の約束はここで無くなる。
- **トークン1本の強度に全部が乗る。** 漏れたら記録が読まれる。長いランダム値にし、
  貼り付け以外の入力経路を作らない。
- **削除の復活は必ず一度は踏む。** step 3 のテストは書いてあるが、**step 5 の配線でも同じ事故が起きる**
  （`clearDeletions` を早く呼びすぎる / `lastSyncedAt` を先に進める）。ここは実機で確かめる。
- 無料枠（D1 の行数・容量、Workers のリクエスト数）は個人利用なら十分だが、**着手時に実測して記録する**。
- 写真を D1 の BLOB に入れる判断は、**同梱データと同じく数字で見直す**（合計が数百MBに向かうなら R2 へ）。
  203件 × 50KB = 約10MB なので当面は問題にならない。

## step 4〜5 の実施記録(2026-08-01)

### 変えた判断(引き継ぎの計画から意図的にずらしたところ)

| 計画                                   | 実装                              | 理由                                                                                             |
| -------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------ |
| `since` は ISO8601 / `serverTime`     | **整数カーソル**(`cursor` + `seq`) | 端末の時計を位置に使うと、時計がずれた端末の行を他端末が二度と受け取らない                        |
| 写真は `records` 表の `thumb` 列       | **`thumbs` 別表**                 | 記録の行が無いうちに写真だけ先に置けない。順序を「写真 → 記録」にできないと写真の無い記録が固定される |
| `crypto.subtle.timingSafeEqual`        | **SHA-256 + 定数時間比較**        | Node に無いので一番落としてはいけない関数だけ単体テスト不能になる。生バイト比較は長さも漏れる      |
| `server/` は eslint の対象外           | **eslint の対象に含める**         | 認証と SQL の勝ち負けが乗っている。React のプラグインだけ外した                                   |
| 秘密は「トークン」（ランダム値の貼り付け） | **利用者が決めたパスワード + 回数制限** | 新しい端末のたびに控えを持ち歩くことになる。覚えられる言葉を許す代わりに、接続元ごとに15分10回で断る |

### 実測(すべてこのブランチで確認)

- **`aliasKey` の NUL 区切りは D1 を往復しても潰れない**(懸念されていたが実測で否定。区切り文字は変えない)
