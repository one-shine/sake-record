# SPEC — 日本酒 記録アプリ（saketime）

## 目的 / 背景

2020-12 から続けている日本酒の飲酒記録（203本 / Excel + 写真）を、記録しやすく振り返りやすいアプリに置き換える。

現状の記録は「何をいつ飲んだか」の台帳でしかなく、**味の傾向を振り返る手段がない**。自分で味の軸を毎回入力するのは飲みながらでは続かないため、**銘柄に紐づく味のデータは外部（さけのわデータ）から取得し、自分は評価とメモだけ入れる**という分担にする。

できあがりの状態: スマホで写真を選んで銘柄をサジェストから選ぶだけで1本が記録でき、PC でも同じ URL を開いて「時系列 / 統計 / フレーバー分布 / 産地マップ」の4視点で203本+今後の記録を振り返れる（5つ目の「知る」は記録に依存しない基礎知識と出典の置き場）。

## スコープ

### やること

1. **記録の作成・編集・削除** — 写真（端末の写真アプリで撮影済みのものを選択）、日付、銘柄（サジェスト）、スペック（自由文）、5段階評価、飲んだ場所・店名、メモ
2. **銘柄サジェスト** — バンドル済み3264件をインクリメンタル検索。選択で都道府県・蔵元・フレーバー6軸が自動で埋まる
3. **手動紐付けUI** — 未紐付けの記録に対し、さけのわ銘柄を検索して手動で紐付ける。紐付け結果はエイリアスとして永続化し、以降の同名表記に自動適用
4. **5つの閲覧画面**
   - 時系列リスト（サムネイル付き・新しい順・検索/絞り込み）
   - 統計ダッシュボード（本数・年別・都道府県別・スペック分布）
   - フレーバー分布図（6軸レーダー / 散布図。自分がなぞっている味の領域と空白地帯）
   - 産地マップ（都道府県SVGを本数で塗り分け、未進出県を可視化）
   - 知る（基礎知識と出典/ライセンス） — **6つの下位タブ（種類 / ラベル / 季節 / 産地 / 味 / アプリ）に分かれ、1画面に1トピックだけ出す**（1枚に積むと 390px で 5,000px を超え、読みたい話に着くまでが全部スクロールになる）。タブ帯は上端に貼り付き、切り替えたらスクロールは先頭へ戻る。**タブは読む人の関心で割る**（実装の都合で割らない）: 種類（どういう酒か・特定名称8種の表）／ラベル（語と数字）／季節（新酒・ひやおろし等）／産地（酒どころ・蔵の数・酒米・地図の見方）／味（6軸の配置図・味タグ）／アプリ（記録の保存とバックアップ・スタイル分布の数え方・銘柄の紐付け・出典とライセンス）。**平易さを優先する**（個人利用のアプリなので法令上の厳密さは求めない。出所バッジ・「確認できていない」の断りは置かない）。ただし**特定名称8種の表だけは国税庁の告示から写した値**を使い、出典と取得日を出典タブに残す。**説明のために作った数字や図（架空の値のチャート）は置かない**
5. **インポート / エクスポート** — 全記録をJSONで入出力。既存203本の取り込みも同じ経路
6. **さけのわデータの定期自動更新** — GitHub Actions で月次取得し、差分があればコミット→再デプロイ
7. **PWA** — ホーム画面追加・オフライン動作
8. **クレジット表示** — **全画面のフッタに1行**でさけのわのクレジットと `https://sakenowa.com` へのリンクを常設する（5タブすべてがさけのわデータを使うので、さけのわの条件「利用している箇所に併記」を満たすには全画面に要る）。地図の CC-BY 4項目（作者・タイトル・ライセンスへのリンク・改変した旨）は**使用箇所（産地タブ）と「知る」タブ**に置く。**フッタには置かない**（本アプリは URL ルーティングを持たず CC-BY §3(a)(2) の「URI で必要情報の場所を示す」枝に乗れないため、併記は使用箇所そのもので満たす）
9. **ラベル写真からの OCR（銘柄サジェストの補助。銘柄を確定する機能ではない）** — 選んだ写真の**原寸の元ファイルを長辺2000pxに縮め、紙の質感を局所適応二値化で落としてから**端末内で OCR をかけ、読めた文字から**銘柄の候補を数件に絞って提示する**。以下がこの機能の定義であり、崩れたら補助として成立していない:
   - **銘柄を自動確定しない。** 提示するのは候補で、**選ぶのは本人**。選んだ結果は既存の銘柄サジェストと同一の経路（同じ紐付け・同じ `linkStatus`）に合流する
   - **写真は端末外に出ない。** クラウド OCR / 外部 API を使わない。エンジン（wasm・worker・日本語学習データ）は同一オリジンに同梱し、オフラインでも動く（初回だけ取得が要る）
   - **外したときに、もっともらしい別銘柄を上位に出さない。** 読み取れない・確度が足りないときは「読み取れなかった」と言い切って**手で選ぶ経路に誘導する**（既存の銘柄サジェストは常に使える）。助言は**まだ試していないこと**だけを言い、失敗欄から「一覧から選ぶ」を直接開けるようにする
   - **文字の場所は自動で提案し、外れたら人が枠で囲める。** ラベルらしい範囲（文字密度）を自動で絞って読み、**候補が出なければ全体も読んで合算する**（自動で悪化しない）。読んだ範囲は画面に明示する。手動の「ラベルを囲んで読み取る」は自動の枠を初期値にして引き直せる。囲んだ範囲は原寸から切り出して**同じ認識経路**に流す（手動の切り出しに失敗したら全体に黙って落とさず、読めない形式だと言う）。**これは場所の提案であって内容の判定ではない** — どの経路でも候補の門と選ぶ人は同じ
   - **絞れなかったときは「読めた字」を絞り込みの鍵として押せる形で出す。** 候補の門を緩めて当てずっぽうを増やす代わりに、押すのは本人という形にする。押した先に出るのは**手で打つときと同じ銘柄サジェストの一覧**で、ここでも候補は作らない
   - **受け皿がある前提で、候補の門はむしろ厳しくする。** 部分一致は銘柄名の**2/3以上**が読めていること、**当たった字が読み取り文字列の1か所に固まっていること**、**ラテンだけの銘柄名は綴りそのものが読めていること**（3字以下は対象外）を要求する。いずれも実物のラベルで別銘柄を1位に出した実例に対応する
   - スペック（「純米大吟醸」等）は自由文なので、読めた語は**補助入力**として欄に足す。銘柄と違い確定の意味を持たない

10. **一覧から銘柄を選ぶ（打たずに辿る三段: 都道府県 → 蔵元 → 銘柄）** — 検索は**銘柄名の字を知っている**ことが前提で、読みのデータを同梱していないので `きど` では `紀土` に届かない。OCR も実測で9枚中3枚は銘柄の字を1文字も読めない。**ラベルから確実に読めるのは蔵元名と都道府県**なので、そこから辿れる道を1本置く:

- **既定は畳んでおき、一段ずつ出す。** どの段にも件数を添える（押す前に絞り込みの効き目が分かる）
- **行き止まりを作らない。** 銘柄を1件も持たない県・蔵元は並べない
- **知らないキーで「全件」に落ちない**（`linkBrand` / `suggest` と同じ規律）
- 選んだ結果は**同じ `handlePick`** に入る（紐付けの経路を入口ごとに分けない）

11. **端末間の同期（本人の端末どうし）** — スマホと PC で同じ一覧が見えるようにする。**本人が用意した同期先**にだけ記録を置く（第三者のサービスに預けない）。

- **同期の単位は記録1件**で、`updatedAt` が新しいほうを採る。**全文書の置き換えにしない**（片方の端末の追加が丸ごと消える）
- **削除は削除として運ぶ**。消した記録が次の同期で復活しない（サーバとローカルの両方に削除の記録を残す）
- **同期は足すものであって前提にしない**。設定していない端末・通信できない端末でも、記録の作成から閲覧まで全機能が動く
- **競合で負けた側を黙って消さない**。両端末で同じ記録を編集したときは、採った側と理由を出す
- 秘密は**パスワード1つだけ**（利用者名を持たない。利用者が1人しかいないので選ぶ相手がいない）。同期先の URL は秘密にしない（環境変数を使わない方針を保つ）
- **パスワードは利用者が決める。** ランダムな長い値を貼り付ける形にすると、新しい端末で使うたびに控えを持ち歩くことになる。代わりに**サーバ側で回数制限をかける**（同じ接続元から15分に10回間違えたら断る）— これが無いと、覚えられる長さの言葉は機械で総当たりされる。**正しく入力できたら打ち間違いの記録は消す**（溜め込むと、次の日の1回の打ち間違いで締め出される）

### 画面に置かない表記（2026-07-26 に削除した）

- **「20歳未満の飲酒は法律で禁止されています」をフッタから削除した。** Phase 1 で自主的に足したもの（BACKLOG B8。起票理由は「無いと不注意に見える」だけ）で、**表示義務の法的根拠は本 SPEC・BACKLOG・第三者ライセンスのいずれにも無い**。フッタを1行に圧縮する（利用者の要望）うえで、義務のある表示（さけのわのクレジット）と義務のない自主表記が同じ密度で並ぶのをやめた。削除の履歴は B8 と B55 に残す。`README.md` には残す（配布物ではなくリポジトリの読み手向けの断り書きなので、画面の情報密度の判断とは別）

### やらないこと（恒久）

- **SNS共有・公開機能** — 記録を他人に見せる導線は作らない。記録は**本人だけが読める場所**にしか置かない
- **写真・記録を第三者のサービスへ預けること**（クラウド OCR / AI API / 解析サービスを含む）。スコープ9の OCR が端末内実行に限られるのはこの恒久方針の帰結であって、**将来クラウドへ出す拡張余地ではない**

> **2026-08-01 に「データは端末内に閉じる」をやめた。** 利用者の要求が変わった（「スマホと PC の両方で同じ一覧を見たい」）。
> **恒久方針として残るのは「第三者に預けない」のほうで、「端末から出さない」ではない** — 記録は
> **本人が用意した同期先**（自分のアカウントで立てたサーバ）にだけ出る。この線引きが崩れると
> スコープ9（端末内 OCR）の根拠も一緒に崩れるので、**同期先は本人のものに限る**ことを条件として書く。
> 経緯と計画は `docs/phases/PHASE_8.md`、起票は BACKLOG の B69。

### やらないこと（今回のリリース。将来の拡張余地として残す）

- **ラベル写真からの銘柄の自動確定 / AI 認識**（スコープ9で入れたのは**候補を絞る補助**まで。読み取り結果で `linkStatus` を決めたり本人の確認なしに銘柄欄を確定したりはしない）
- 在庫管理・未開栓管理（「飲んだ記録」に徹する）
- 価格・購入先・同席者・温度帯の記録項目
- **他人と共有する機能・複数利用者**（同期は**本人の端末どうし**に限る。招待・共有リンク・公開プロフィールは作らない）

### 決定に由来する制約（トレードオフとして受け入れる）

- **同期を設定していない端末では端末間同期は無い。** 保存先の第一は変わらず IndexedDB で、別端末へはJSONエクスポート/インポートでも移せる。**同期は足すものであって前提にしない**（設定していない端末・通信できない端末でも全機能が動く = A28）
- **ブラウザのサイトデータ削除で端末内の記録が消える。** 同期を設定していればサーバから戻せるが、**定期的なJSONエクスポートはやめない**（同期先が1つしか無い状態は、バックアップが1つも無い状態と大差ない）。アプリ側の「最終エクスポートからの経過日数」の警告も残す
- **写真の原本はアプリが持たない。** カメラアプリで撮った原本は端末のカメラロールに残り、アプリは長辺400pxのサムネイルのみ保持する

## 前提（本SPECで採用する技術判断）

| 項目       | 決定                                                                                                                                                        | 理由                                                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| スタック   | Vite + React + TypeScript                                                                                                                                   | poker-gto と同構成。既存の CI/デプロイ知見をそのまま流用できる                                                                  |
| ドメイン層 | `src/domain/` は React 非依存の純TS                                                                                                                         | 既存方針「計算コアをフレームワーク非依存に保つ」。外部依存なしで単体テストする                                                  |
| 永続化     | IndexedDB（薄いラッパを自作、`src/store/`）                                                                                                                 | 依存を増やさない。スキーマが単純（1ストア+索引）                                                                                |
| テスト     | Vitest                                                                                                                                                      | 単一テスト実行が速い                                                                                                            |

**同梱データの置き場は `src/data/` ではなく `public/data/` にした**（計画からの逸脱。BACKLOG B2）。理由は3つ:

1. **Service Worker の原子的シェルに安定した既知パスを書ける。** `src/` に置くとバンドラが名前にハッシュを付けるので、`sw.js` にプリキャッシュ対象として直接書けない（オフライン起動の保証が弱くなる）
2. **月次更新が JS バンドルのハッシュを変えない。** さけのわが1件増えただけで全利用者がアプリ本体を再取得する状態を避ける
3. **232KB の JSON を `tsc` の入力から外せる**

`src/data/` に残るのは**手で書く表だけ**（`brand-aliases.ts` / `brewery-articles.ts`）。生成物は `public/data/` の下に置き、gzip 後の合計サイズは `npm run data:check` が `public/data/` **全体**に対して 200KB 以下を検査する。

### 不確実性の表示規約

既存方針「不確実性は隠さず信頼度を明示する」に従い、**紐付いていない記録にフレーバー値を推定で埋めない**。

- `unlinked` / `unknown` の記録は、フレーバー分布図で「フレーバー未取得」として件数のみ表示し、6軸の集計から除外する
- 集計は必ず「分母 = フレーバー取得済み件数」を併記する（203本中190本、のように）
- `linkStatus` を UI のバッジとして出す。`manual` は本人が判断した紐付けであることが分かるようにする
