- **OCR の律速が「認識」ではなく「検出・分割」であることを実測で切り分けた（2026-07-28(8)。利用者の指摘「文字の読み取りアルゴリズムは論文などいろいろ研究されていて精度は高いはず。アルゴリズムは問題ないか？」）。** **指摘は正しく、アルゴリズムの選択がいまの最大の限界。** 切り分けの実測（合成シーン9枚 = 瓶の全体が写る写真）:
  - **認識側は仕事をしている。** 銘柄の列だけを正しく切り出して二値化した理想的な入力なら、`jpn` + PSM6 で **当たった字 12/19・全字読めた銘柄 4/9**。しかも**倍率に鈍感**（1文字24px で 9/19 → 40px で 12/19 → 200px で 11/19）なので、**文字高の正規化は梃子ではない**
  - 同じ理想入力で **`jpn_vert` + PSM5 は 5/19・2/9**。縦書きの列でも横書きモデルの方が2倍以上当たる（ただしアプリは既に `jpn` PSM6 を1本目に走らせているので、ここに無料の改善は無い）
  - **律速は切り出し。** アプリの自動検出が出すのは「ラベルの範囲」でありスペック欄・縁・背景を含む。**テキスト行の検出を自作のヒューリスティクスで足すと逆に悪化した**（インクの連結成分を列としてまとめ、列ごとに認識 → **4/19**）。学習済み検出器（EAST / CRAFT / DB）が使われるようになったのはまさにこの理由で、ヒューリスティックな分割は2015年前後に置き換えられている
  - **手で狭く囲んでも端から端までは届かない**（実 Chromium で 候補1 + チップ6 = 7/9。自動の 8/9 を下回る）。読みは惜しいところまで来る（`独祭` / `2穂` / `血今` / `逢来果`）が、被覆率 2/3 の門に届かない
  - **tesseract は文書OCR**（平らな紙に整列した行を前提）。瓶のラベルは曲面・斜め・装飾書体で、研究上は**シーンテキスト認識**という別問題（検出 DB/CRAFT/EAST + 認識 CRNN/SVTR/PARSeq）。「OCR の精度は高い」は文書OCRの話で、この課題には当てはまらない
  - **段差のある選択肢**: 端末内でシーンテキストのモデルに載せ替える（ONNX Runtime Web + PP-OCR mobile の日本語モデル）。資産は **7.7MB → 概算25〜30MB** で、**SPEC の上限12MB（受け入れ基準 A20）を超える**ので仕様判断が要る（→ **B67**）
  - なお**この限界はアプリの設計が既に吸収している**: 認識が 12/19 しか読めなくても到達は 8/9 まで来る（候補 → 読めた字で絞る → 一覧から選ぶ → 打って探す の段）
- **紙の質感を二値化で落とし、1字の銘柄名を候補から外した（2026-07-28(7)。利用者の指摘「読めた文字数とラベルの文字数が違うが、画像処理がうまく行っていないのでは？」）。** **指摘は正しかった。** ラベルには20〜30字しか無いのに読み取りは200字を超えており、中身は **`ー` と `ニ二三` だらけ = 紙の横リブ（畝）を長音符として読んでいた**。tesseract 自前の大域二値化では紙の質感も照明むらも落とせない。→ **局所適応二値化**（`src/lib/ocr/binarize.ts`。局所平均との比と絶対差の両方で判定、積分画像で O(w×h)）。**掛ける条件と定数はすべて実測で決めた**: (a) **中間調（64〜191）が5%未満の画像には掛けない** — 既に白黒に近い画像に掛けると落ちる（合成の綺麗なラベル 8/9 → 6/9 で再現）。5%は谷で、実測は **綺麗なラベル 0.2〜0.4% / 瓶が写るシーン 17.3% / 写真ふう 67.3% / 利用者の実機 63.1〜66.2%** と2桁離れている (b) **比 0.85 + 絶対差 24階調** — 比だけ（0.92）だと暗い場所やぼけで地の全面がインクになり（インク率 21.7%）、読み取りが数千字に膨れた (c) **縮小も二値化も要らない画像は再エンコードしない**（無意味な JPEG 再圧縮だけで読み取りが落ちるのを実測）。**実測（本番ビルド・実 Chromium・ボタン1回）: clean 8/9（不変）/ シーン 8/9（候補が 3→4 に増）/ 写真ふう 7/9（不変）**。実機のラベルでは `會津` が読めるようになった。**あわせて1字の銘柄名を候補から外した**（B49 に残していた50件）— 実機の写真で `回` と `作` が候補に並んだ（ラベルのどこにも無い）。1字の名前は全字一致が定義上つねに成立するので被覆率でも近接でも切れず、80字超の読みでは稀な1字がほぼ確実に現れる。**1文字一致だけで候補に上がれる銘柄は 50 → 0件**（門が無ければ1270件だった）。チップからは従来どおり届く。`npm run ci` exit 0（**56 files / 1325 passed | 24 skipped**）。変異5件で赤を実演（1字の銘柄名も候補にする / 絶対差の門を外す / 比を緩める / 大域の固定閾値にする / 許容を無くす）
- **読めなかったときの逃げ道を作り、装飾書体が読めないことを実測で確定させた（2026-07-28(6)。利用者の実機スクリーンショット2枚目「まだ全然読めていない」）。** **(1) 助言が「やった操作をやり直せ」になっていた。** 利用者はラベルを狭く囲んで読ませて失敗したのに、画面は「『ラベルを囲んで読み取る』で銘柄の文字だけを囲むと読み取りやすくなる」と返していた。→ 助言を**読んだ範囲（`scope`）で出し分ける**ようにし、囲んだ後の失敗には「装飾された字体は写真から読み取れないので一覧から選ぶのが確実」と言う。**(2) 失敗欄から「一覧から選ぶ」を直接開けるようにした**（`BrandBrowser` の開閉を `RecordForm` に持ち上げ、`OcrAssist` に `onBrowse` を渡す）。一覧は写真欄より上にあるので、押さないと気付けない位置だった。開くときは `scrollIntoView`（jsdom に無いので optional call）。**(3) 装飾書体は原理的に読めないことを確定させた。** 利用者のスクリーンショットからラベルを切り出して tesseract に直接かけたところ、**3パスのどれも `會津` `宮泉` を1字も出さない**（出たのは `当当放つ…5breguike` = "premium sake" の誤読）。一方**ふりがな「みやいずみ」は正確に読めている**。つまりこのラベルで読める唯一の正しい信号は読み仮名だが、**さけのわの brands は `id`/`name`/`breweryId` だけで読みを持たない**ので銘柄に結び付けられない（公式ドキュメントで確認）。**(4) チップの並びでは救えないことも確定。** 別の回で `宮`(11件) が読めていたが、チップは希少順の上位8で、**誤読字のほうが稀**なため `宮` は **63字中25位**。上限を24に上げても届かない（=この写真は銘柄欄に `宮` と打つのが最短）。**実 Chromium で通しの確認**: 実機のラベル写真 → 候補0 → 失敗欄の「一覧から銘柄を選ぶ」→ 福島県 → 宮泉銘醸 → 宮泉 で県・蔵元まで入る。`npm run ci` exit 0（**55 files / 1311 passed | 24 skipped**）。変異3件で赤を実演（囲んだ後も同じ助言を出す / 逃げ道のボタンを出さない / 押しても一覧を開かない）。**利用者の写真は追跡しない**（`docs/evidence/` の規律）
- **雑音が銘柄名を丸ごと覆う穴を塞ぎ、検出を質感に強くした（2026-07-28(5)。利用者の実機スクリーンショット「全く文字が読み取れていない」）。** 画面には候補が3件出ていたが**全部誤り**で、しかも `Bange Yamada Hanjukunama`(12字中12字) / `カフェSAKEしろいスパークリング`(17字中14字) / `Wakanami Sparkling`(11字中11字) と**全字一致を主張**していた。**(1) 原因は「文字を集合としてしか見ていない」こと。** 読めた文字は**異なり字87**の雑音で、この規模になると銘柄名の字が「読めた」のではなく雑音がたまたま全部含んでしまう。希少性は全字一致では**和**を取るので12字当たれば必ず閾値を超える = 希少性も被覆率も無力。→ **近接の門**を足した（`minimumWindow`。当たった字を全部含む最短の窓が `一致字数 × 2 + 2` 以下）。ラベルの銘柄名は1か所に固まって印字されるという事実が根拠で、**この層は位置の情報を丸ごと捨てていた**。あわせて照合の入力を**パスごとの配列**にした（塊をまたいだ寄せ集めを近接の証拠にしない）。**(2) ラテンはそれでも残った。** `Femiurmsake`（ラベルの英字の誤読）という**連続した11字**に `MIRU` `USUKI` `SUMI` `afs` が全部収まる — **字種が26しかない**ので文字集合という模型がそもそも成り立たない。→ ラテンだけの銘柄名（130件）は**綴りそのもの**を要求し、**3字以下は候補にしない**（`yu` が2字の `Yu` に一致した）。実機の読みに対する候補は **3件（全部誤り）→ 1件（`會津`。ラベルに実際に印字されている字）**。9枚の実測は**一切劣化なし**（誤候補0件・到達6/9のまま）。**(3) 位置検出が石の天板を掴んでいた。** 実機写真をスクリーンショットから切り出して検出にかけると、枠は**画像下端の天板**（`y=0.94`）でラベルを完全に外していた。原因は**平均勾配**で、石・布・木目のような細かい質感は弱い勾配が一面にあるので平均が文字より高くなる。→ **強い縁（隣との差50以上）を持つ画素の割合**に替えた（文字は「本数は少ないが非常に強い縁」）。走査は 平均 / 強い縁30・50・80 / stride2 × 比 0.3〜0.5 の15通りで、**強い縁50 × 比0.3 が最良**（合成9枚+実機1枚で 9/10・null 0。実機も銘柄の字に当たる）。**実測（本番ビルド・実 Chromium・ボタン1回）: シーン 7/9 → 8/9 / 写真ふう 7/9 / clean 8/9**。`npm run ci` exit 0（**55 files / 1306 passed | 24 skipped**）。変異7件で赤を実演（近接の門を外す / ラテンの綴り要求を外す / 塊をまたいで窓を測る / ラテン判定を常に false / ラテンの最短長を外す / 平均勾配に戻す / 縁の閾値を1に下げる）
